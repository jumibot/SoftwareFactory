## 1. Servidores MCP de kanban/tareas e integraciones de tareas con Claude Code: qué se puede reutilizar para JKanban

### Takeaway
No hay un servidor MCP de kanban sobre SQLite maduro que encaje con JKanban tal cual; lo reutilizable son **patrones**: el modelo de Backlog.md (CLI + MCP + web sobre archivos, JSON versionado `--json`, entidades «decision»/«draft»), el de beads (`bd prime` inyecta contexto, `bd remember`, instalación de hooks para Claude Code) y el de claude-code-kanban (leer las tareas y transcripciones que Claude Code ya escribe en el directorio de configuración). task-master tiene licencia MIT + Commons Clause y requiere claves de API propias; vibe-kanban está en cierre (*sunsetting*).

Gestor de tareas y kanban en Markdown dentro de cualquier repo Git: tablero en terminal (`backlog board`), web local (`backlog browser`), «local-first, sin servidor, sin cuenta, sin telemetría», conector MCP que autoconfigura Claude Code/Codex/Gemini/Kiro/Cursor; los comandos de lectura dan «JSON estable y versionado» con `--json` (`task list`, `task view`, `decision list`, `search`); recomienda «una tarea por sesión de agente, un PR por tarea» — [README](https://github.com/MrLesk/Backlog.md)

### Inferences
- Para JKanban (FastAPI + SQLite sin ORM) lo más barato es escribir un MCP propio y pequeño (p. ej. FastMCP en Python, mismo proceso o proceso aparte que llame a la API REST), tomando ideas de la superficie de herramientas de Backlog.md (`task list/view`, `decision list`, `search`, salida JSON versionada) y del patrón `prime`/`remember` de beads para el contexto de SessionStart.
- La entidad «decision» de Backlog.md se parece a la bandeja de decisiones de la SF; conviene estudiar su formato antes de diseñar el esquema.
- Riesgos: task-master (Commons Clause, depende de claves de API, lo que choca con la política de suscripción frente a clave de la SF) y beads (modifica `AGENTS.md` e instala hooks por defecto; se instala con `curl | bash`) no deben adoptarse sin revisión. vibe-kanban: proyecto en transición a mantenimiento comunitario, mala base para depender de él.

## 2. Colecciones de hooks y observabilidad (dashboards, ccusage, claude-code-log, visores de sesión, status lines)

### Takeaway
Hay una arquitectura de referencia clara para telemetría por hooks: el proyecto de disler (hooks → HTTP POST → servidor → SQLite → WebSocket → UI), que coincide con lo que haría JKanban con *http hooks*. Pero **no tiene licencia** (no se puede reutilizar código, solo la idea). Para coste y uso, ccusage (MIT, muy activo) es la referencia; para status line, ccstatusline (MIT) y claude-powerline (MIT).

## 3. Historial y resumen de sesiones entre proyectos, «dónde lo dejé» y memoria

### Takeaway
Hay varios visores locales y de solo lectura sobre `~/.claude/projects` (claude-session-dashboard, claude-code-karma, claude-code-history-viewer, agent-sessions) y gestores de sesiones (ccmanager, claude-squad). En memoria, claude-mem es el más popular (103k★), pero es pesado: tiene servicio worker, resúmenes con IA y un modo alojado de pago por defecto en algunos instaladores. Los datos de sesión de Claude Code se borran en unos 30 días, lo que obliga a la SF a persistir sus propios resúmenes.

### Inferences
- Para «dónde lo dejé» y el daily, la SF no necesita una memoria vectorial: le basta persistir en JKanban un resumen al cerrar (Stop/SessionEnd) e inyectarlo en SessionStart con `additionalContext`. claude-mem y beads hacen exactamente eso, como prueba del patrón.
- Como Claude Code purga las sesiones (unos 30 días según karma), el backend debe copiar o resumir lo que necesite antes de esa purga.
- Riesgo de claude-mem: el opt-in de nube por defecto, el worker residente y el envío de observaciones a terceros chocan con la separación entre brain y KB y con la política de datos de la SF. Solo sirve como referencia de diseño.
- AGPL (basic-memory, claude-squad, opcode, claudecodeui) impide incorporar código a un backend propio sin las obligaciones copyleft. Usarlos sin modificar como herramienta no tiene ese problema.

### Gaps
- No comprobé si claude-session-dashboard o karma exponen una API o exportación aprovechable desde JKanban.
- No encontré ninguna herramienta madura de «daily entre proyectos» que combine kanban, sesiones y decisiones. Los generadores de standup encontrados se basan en git, son de muy baja adopción o están descritos solo en directorios.

## 4. Notificaciones y atención

### Takeaway
El mejor candidato de notificaciones es agent-notifications (GPL-3.0, Windows incluido, webhooks), aunque instala hooks, un MCP y una skill. Con ntfy (Apache-2.0, 35k★) como transporte, un http hook o un script mínimo propio basta. Los aprobadores remotos de permisos vía ntfy (claude-push, claude-remote-approver) son pequeños y de riesgo alto.

## 5. Dashboards locales o de escritorio que agregan muchos repos

### Takeaway

### Inferences
- La SF puede tomar de estos paneles la lectura de `~/.claude/projects` y de estados en vivo, y centrar su propio valor en la capa de portfolio: WIP, decisiones, daily y cierre sobre JKanban.
- Seguridad transversal: los hooks y las status lines ejecutan comandos arbitrarios con los permisos del usuario. Los instaladores `npx …`/`curl | bash` (claude-mem, beads, history-viewer, ccusage vía npx) son vectores de cadena de suministro. Si se adopta algo, fijar versiones, leer el código de los hooks y preferir herramientas de solo lectura (claude-code-log, karma, session-dashboard).

### Gaps
- Las estrellas y las fechas cambian rápido. No verifiqué el número de mantenedores, el bus factor ni las incidencias de seguridad abiertas de ningún repo.
